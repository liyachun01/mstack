## Why the reviewed v2.4.22 tag is not acceptable as our default

1. **Framework security baseline:** the tagged lock selects Next 15.4.8; Next's published December 2025 security update requires at least 15.4.10 for that release line. This establishes a known stale source baseline, not an exploit test of a pulled image. The upstream Dockerfile also performs an unfrozen production dependency install, so runtime packages cannot be inferred solely from the source lock. We did not pull or scan the image. [Next advisory](https://nextjs.org/blog/security-update-2025-12-11), [tagged Dockerfile](https://github.com/metatool-ai/metamcp/blob/32b6e9813acfc13d1013eb2452be1899d6654bb9/Dockerfile).
2. **MCP SDK baseline:** TypeScript SDK 1.16.0 precedes security fixes, including the HTTP DNS-rebinding-default advisory fixed in 1.24.0. Exploitability depends on authentication, transport and application defenses; a loopback port alone is not an adequate security assertion. [SDK advisory](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-w48q-cv73-mx4w).
3. **Tool filtering:** official tagged `getToolStatus` catches database errors and returns `null`; the call check treats `null` as allowed. This is a directly observed **fail-open permission path**. It can block deliberately inactive tools under normal conditions but must not be presented as our hard authorization boundary under failure. [Tagged filter implementation](https://github.com/metatool-ai/metamcp/blob/32b6e9813acfc13d1013eb2452be1899d6654bb9/apps/backend/src/lib/metamcp/metamcp-middleware/filter-tools.functional.ts).
4. **User separation:** an open upstream report describes authenticated users reading/writing others' stored OAuth credentials. The old tagged router also uses `protectedProcedure` without supplying caller identity to those operations. We confirmed that route shape, not every exploit condition. Do not use this as a shared team service merely because it has accounts. [Issue 345](https://github.com/metatool-ai/metamcp/issues/345), [tagged OAuth router](https://github.com/metatool-ai/metamcp/blob/32b6e9813acfc13d1013eb2452be1899d6654bb9/packages/trpc/src/routers/frontend/oauth.ts).

The fork changes failure handling and admin-gates raw OAuth operations, but **still allows newly unmapped tools by default**. Thus it is not automatically a positive allowlist. Namespace filtering must be tested at both discovery and dispatch, including new-tool synchronization, alternate routes and failures. Keep the Graphify/CodeGraph child-side restrictions as defense in depth. [Fork filter](https://github.com/Umbrella-IT-Group/metamcp/blob/b0ef1856ddf5e95ca2641009fd761a323fa03254/apps/backend/src/lib/metamcp/metamcp-middleware/filter-tools.functional.ts), [fork OAuth router](https://github.com/Umbrella-IT-Group/metamcp/blob/b0ef1856ddf5e95ca2641009fd761a323fa03254/packages/trpc/src/routers/frontend/oauth.ts).

The concrete call-check failure path, when a cached status does not resolve it, is: **permission query throws → `getToolStatus` returns `null` → `isToolAllowed` treats `null` as allowed**. Its outer error handler also permits the call. This proves an authorization decision can fail open, not that every database outage necessarily executes a tool; other request stages may fail too. The newer official branch retains this behavior. [Pinned official development filter](https://github.com/metatool-ai/metamcp/blob/ff4ff2de9d25453c52dcc7be32680b30700a6012/apps/backend/src/lib/metamcp/metamcp-middleware/filter-tools.functional.ts), [development lock](https://github.com/metatool-ai/metamcp/blob/ff4ff2de9d25453c52dcc7be32680b30700a6012/pnpm-lock.yaml).

## Better fixes and what a custom build means

Changing only the base image or rebuilding the existing Dockerfile does **not** repair permission logic or establish patched application dependencies. ARM64 is not the reason to reject the reviewed official artifacts: v2.4.22 and both checked 2.5.x images already support it. The Umbrella fork's missing native ARM64 image is an additional cost of choosing that fork.

| Approach | What it fixes / what remains | Return-to-official implications |
| --- | --- | --- |
| Official image with loopback/authentication and child tool gates | Reduces exposure and limits child operations; does not fix the source-level fail-open permission path or prove the dependency inventory is patched. | Few packaging differences, but not an adequate basis to claim gateway authorization is enforced. |
| Pinned official source with container packaging only | Can improve supported runtime and lock fidelity; application behavior remains unchanged. | Usually the simplest image cutover if schema and configuration remain compatible; packaging alone does not meet the identified repair requirements. |
| Pinned official source plus reviewed security patches, without schema divergence where feasible | Update audited dependencies/lock; distinguish lookup failure from absent mapping; deny failed/unresolved/unknown calls; test discovery and execution; enforce OAuth ownership or reviewed route restrictions. | Best candidate for an upstream-friendly repair, but only after patch scope and schema/auth compatibility are proven. We own the patches until upstream incorporates equivalent fixes. |
| Pinned Umbrella application fork plus ARM64/supported-runtime packaging | Existing failure-handling/auth/session improvements, with additional features and migrations. New tools are still not automatically allowlisted. | Not a safe image-only downgrade; needs credential/configuration/schema migration qualification. |
| Wait for a qualified official release; propose direct harness connections meanwhile | Avoids maintaining gateway patches now, but postpones gateway functionality. | Lowest gateway maintenance, but changes setup order and requires a separate user decision. |

For the upstream-derived repair candidate, a future exact proposal must identify the complete dependency/patch inventory, preserved migration files/schema, tested runtime and patch maintenance owner. Avoid adding fork-only RBAC/audit features merely to fix the authorization failure. Do not promise the repair is only a few lines: SDK/framework/auth upgrades and backported fixes may require broader changes. If qualification discovers necessary schema/auth divergence or an unmanageable patch set, report it before selecting a different approach.

Required future regression checks include disabled tools, newly introduced/unmapped tools, malformed names and unresolved servers, lookup failures with cache hits/misses, permission-cache invalidation, alternate dispatch routes, credential ownership, two independent clients, session recovery and tool-call replay behavior. Tests must prove both what is listed and what can actually run. Local-only access is defense in depth, not a substitute for these checks. No patches or tests of MetaMCP runtime have been performed in this documentation step.

## Is changing back to an official image easy?

**Packaging-only or truly schema-preserving patches:** potentially straightforward, not guaranteed. The future official target must include equivalent fixes and support the same schema/auth/configuration. Compare migrations and schema, rehearse startup on an isolated database copy, run the regression suite, then cut over the image/digest through its own approval. Do not remove a necessary patch just to regain the official label or switch to the rejected old release.

**Full Umbrella fork:** there is direct evidence against calling this a drop-in rollback:

- Official v2.4.22 declares `api_keys.key` as a required plaintext column. The fork's migration `0034` backfills `key_hash`/`last4` and **drops `key`**. Pointing that official code at this migrated database can break its queries; one-way hashes cannot reconstruct the removed secrets. [Official schema](https://github.com/metatool-ai/metamcp/blob/32b6e9813acfc13d1013eb2452be1899d6654bb9/apps/backend/src/db/schema.ts), [fork API-key migration](https://github.com/Umbrella-IT-Group/metamcp/blob/b0ef1856ddf5e95ca2641009fd761a323fa03254/apps/backend/drizzle/0034_api_key_hash_at_rest.sql).
- Migration `0036` also replaces stored OAuth access/refresh tokens, authorization codes and selected client secrets with hashes; switching application images does not reverse that transformation. The fork adds further session, role, endpoint-access-group and audit state. This is an application/schema fork, not merely a different CPU build. [Fork OAuth migration](https://github.com/Umbrella-IT-Group/metamcp/blob/b0ef1856ddf5e95ca2641009fd761a323fa03254/apps/backend/drizzle/0036_oauth_credentials_hashed_at_rest.sql).

Safe planned exit: keep reviewed secret-free gateway desired-state definitions outside the database; qualify the actual future official release; populate a fresh, dedicated gateway database through a verified configuration translation/apply procedure; reissue keys/re-authorize clients when representations differ; test routing and every integrated harness; retain the previous image/database for a reversible cutover. A pre-fork database restore is another rollback option only if one exists and its loss of subsequent gateway changes is explicitly accepted. No compatible exporter, translator or restore procedure is implemented yet.

Basic Memory's database/Markdown and Graphify/CodeGraph source/index state stay separate from gateway state, so this planned gateway migration should not require rebuilding the memory layer. This separation does not make gateway credentials or configuration automatically portable. Never start an old image against a live fork database to "try" compatibility; startup runs migrations. Backups and tests on an isolated copy come first.

## Connection plan: preserve container boundaries

MetaMCP's STDIO configuration launches a process **inside its own container**. It cannot directly launch our existing separate containers without extra plumbing.

Do not solve this by mounting the Docker socket, giving privileged access, passing database/auth secrets to child processes or silently adding a bridge/framework. A combined image containing all tools would also change their existing filesystem/network/credential isolation and needs explicit approval; it is not the default recommendation.

For a later, separately approved integration:

- Prefer authenticated HTTP sidecars on a project-private code network, with only the gateway publishing a loopback port. No public/LAN code-tool ports.
- Pinned Graphify has native Streamable HTTP and API-key middleware using dependencies already in its approved image. Its existing seven-tool adapter is **stdio only**: preserving the same pre-dispatch gate on HTTP must be implemented and tested, not assumed. Wildcard binding disables its native DNS-rebinding guard, so explicit host/origin/auth protection must be reviewed for the private-network design. [Pinned HTTP implementation](https://github.com/Graphify-Labs/graphify/blob/1cd9a36c0c57a661d2d2234bc3207e887e1ba104/graphify/serve.py).
- CodeGraph's reviewed transport source defines stdio and raw local sockets, not an HTTP MCP endpoint. Its daemon socket is **not Streamable HTTP**. A reviewed, pinned stdio-to-HTTP adapter or another deliberate transport plan is still required; no such bridge is currently installed. [Pinned transports](https://github.com/colbymchenry/codegraph/blob/f4ddf508516332419ea3c95702810765936cf679/src/mcp/transport.ts).
- CodeGraph direct mode permits only one MCP writer for the same index. Future gateway pooling must use one process/appropriate sharing or be tested against its daemon design; do not launch multiple writers and assume it is safe. [Pinned CodeGraph documentation](https://github.com/colbymchenry/codegraph/blob/f4ddf508516332419ea3c95702810765936cf679/README.md).
- Basic Memory is not connected while its integration remains deferred. Keep n8n, Codex registration and PKM separate.
